# Phase 1: The Minimum Viable Tool

Piñata's engine works (motion capture with physics, cloth, skins, the page world), but it is reachable only through
proof runners and diagnostics. Phase 1 of the [roadmap](../ROADMAP.md) makes it a tool an AI agent uses to produce
game characters: one command line and an MCP server over it, animations recorded offline for every direction, and
exports a game engine reads. The exit test is the roadmap's: an agent, from a prompt, produces an eight-direction
character with a cape that walks, idles and jumps, skinned, exported as a sprite sheet, passing every gate.

## Design

- **Recorder.** A character's animations are recorded offline with the same pieces the page uses: the player
  (motion matching over the capture clips, jump takes), the secondary motion (cloth, chains), the skins and the strip
  painter. A recording is a scripted run on flat ground: a behaviour (`idle`, `walk`, `run`, `turn`, `jump`, and the
  later additions) is a short command script for the player, warmed up until the motion settles, then cut. Looping
  behaviours (idle, walk, run) are cut at a matching pair of frames (same stance phase, pose and cloth nearest), so
  the loop plays without a seam; one-shot behaviours (jump, turn) run from rest to rest. Each recording is drawn in
  eight directions by turning the character on the spot before recording (the motion is the same; the view sector is
  the direction's), at the skin's own size and the page's camera.
- **Export.** A sprite sheet PNG (one row per animation and direction, frames in order, cells of one size with a
  shared anchor at the ground under the root) and a JSON file in the Aseprite JSON array format that engines and
  tools already read: frames with their rectangles and durations, `frameTags` naming each animation and direction,
  and the anchor as a slice pivot. Then `.aseprite` files (the documented binary format: one layer, tags per
  animation and direction), written without a dependency.
- **One command line.** `pinata` (a `bin` in package.json) with subcommands over what exists: `new` (a starter),
  `check` (the gates and hints), `skin` (preview and fit), `render` (stills and strips for looking) and `export`. Every
  subcommand prints what it wrote and exits non-zero on a failed gate whose fix is in the character's files, with the
  hint naming the file to fix; gates that measure the engine itself (feet held and facing in exports, which no
  character file can fix) are printed as engine notes and do not fail an author's command.
- **MCP server.** `pinata mcp` speaks the Model Context Protocol over stdio (JSON-RPC 2.0; the protocol is small, so
  no SDK dependency): one tool per subcommand, with the same arguments and the same results as the command line,
  plus the authoring guide as a resource. Claude Code and other clients use it directly.
- **Behaviours.** Walk, run, turn and jump exist. Phase 1 adds `idle` (a standing take with breathing and weight
  shifts, from CMU), `crouch` and one simple attack (CMU takes, the knight's with its sword held by the existing
  style), each a recorder script and a gate.
- **Authoring hints.** The P5 authors' notes go into the guide and the hints: decals for small features,
  stride-to-leg-length guidance, palette budgeting, radius against diameter, a reliable edit path for agents; and the
  skin artist's guide joins the authoring guide so one document covers a character end to end.

## Gates (fixed before implementation)

| Gate | Threshold | Notes |
|---|---|---|
| Existing outputs | byte-identical, except outputs named as meant to change | the page and its gates untouched |
| Same input, same export | exporting a character twice gives byte-identical files in Node | determinism per engine |
| Seamless loops | for every looping animation and direction, the pixels changed between the last frame and the first are at most the median changed between consecutive frames of that loop | |
| Feet held in exports | in every walk and run loop, a planted foot's sole pixel moves at most 1 px between frames of one stance | the page's standing rule, on exported frames |
| Every direction | each animation exported in eight directions; a blind panel of the eight idle frames per character names each direction (front, front-left, ...) correctly in at least 90% of answers | facing reads |
| Round trip | an independent reader in the tests rebuilds every exported frame from the sheet and the JSON, and from the `.aseprite` file, bit-exactly | |
| CLI and MCP agree | for every subcommand, the MCP tool with the same arguments writes byte-identical files and returns the same status | a scripted client in the tests |
| Behaviours read | for idle, crouch and the attack, a blind panel names the action from its side-view strip (from a list including distractors) in at least 2/3 of answers per behaviour | |
| Exit test | three prompts for characters with capes, each given to one fresh agent with only the authoring guide and the MCP server (no repository context): each reaches a skinned, exported character passing every gate within 10 `check` runs; three fresh judges match the exported idle sheets to the prompts, passing if each judge matches all three or at least 2 of 3 judges do | the roadmap's exit |

## Batches

- **A. Recorder and export:** recorded idle, walk, run, turn and jump in eight directions for the four humanoids; the
  sheet and JSON; the loop, feet, determinism, direction and round-trip gates (the `.aseprite` part of the round trip
  waits for C). Review.
- **B. One command line and the MCP server:** `pinata` with its subcommands; `pinata mcp`; the agreement gate; the
  guide as a resource; Claude Code configured with the server in the repository's own `.mcp.json`. Review.
- **C. Behaviours and Aseprite:** idle from capture, crouch, the attack; `.aseprite` export; the behaviours gate.
  Review.
- **D. Authoring and the exit test:** the hints and the guide; a compiled JavaScript `pinata` bin (`src/` built to
  `dist/` with `tsc`, as the web build is), so `npx pinata` and `npx pinata mcp` run from an installed package; the
  exit test, its agents using the server through `npx`; release. Review.
- **E. What the exit test met, then the exit test again:** the friction the first exit test recorded, each fixed in
  the tool or the guide, then the exit test run again with fresh agents, the same prompts and the same gate. Gates of
  this batch, fixed before it is built:
  - the left-facing `ground` failures: the cause found in the three authors' skins (the assassin's with its foot
    shown again) and fixed where it lies; if it lies in the engine, those skins pass `ground` in every direction
    without edits, and if in the skins, the hint names the change that makes them pass, and making it does;
  - `export` over MCP: the text result within 4,000 characters for every example and every exit-test author, with
    every `FAIL` line and its hint in it;
  - `check` reports the `ground` gate for the idle in every direction (or says plainly which gates only `export` runs);
  - a foot sprite with no drawn pixels in a view where the foot is shown is an author failure;
  - a `skin.json` error for a misplaced view or part form points to the form expected;
  - the guide says a cape is cloth (`motion.json`) and shows it first among the steps for a caped character;
  - existing outputs byte-identical, or a change accepted with `--accept` and named here with its reason.

### Batch D: the exit test

Prompts, fixed before any author ran (the identifiers `smith`, `assassin` and `ranger` name the author directories):

1. smith: "A squat, broad-shouldered dwarf blacksmith with a bushy orange beard, a leather apron and a short red cape
   hanging from the shoulders."
2. assassin: "A tall, thin assassin in a long black cape that reaches the ground, with a plain white mask and dark
   clothes."
3. ranger: "A green-cloaked ranger with a pointed hood, brown boots and a longbow carried on the back."

Setup: `npm run build`, `npm pack`, and for each author a fresh empty directory outside the repository with the tarball
installed (`npm install <tarball>`, nothing else), `docs/authoring.md` as the only document, and a `.mcp.json` that
starts `npx pinata mcp`; `npx pinata help` worked in each first. Each author ran as `claude -p` on sonnet from its
directory, with the judge runner's isolation (`CLAUDE_CODE_DISABLE_CLAUDE_MDS`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY`,
`--setting-sources ""`, `--strict-mcp-config`), tools `Read`, `Write` and `Edit` and the five pinata MCP tools only (no
