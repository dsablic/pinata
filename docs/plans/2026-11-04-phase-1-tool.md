# Phase 1: The Minimum Viable Tool

Piñata's engine works (motion capture with physics, cloth, skins, the page world), but it is reachable only through
proof runners and diagnostics. Phase 1 of the [roadmap](../ROADMAP.md) makes it a tool an AI agent uses to produce
game characters: one command line and an MCP server over it, animations recorded offline for every direction, and
exports a game engine reads. The exit test is the roadmap's: an agent, from a prompt, produces an eight-direction
character with a cape that walks, idles and jumps, skinned, exported as a sprite sheet, passing every gate.

## Design

- **Recorder.** A character's animations are recorded offline with the same pieces the page uses: the player
  (motion matching over the capture clips, jump takes), the secondary motion (cloth, chains), the skins and the strip
  painter. A recording is a scripted run on flat ground: a behaviour (`idle`, `walk`, `run`, `turn`, `jump`, and the
  later additions) is a short command script for the player, warmed up until the motion settles, then cut. Looping
  behaviours (idle, walk, run) are cut at a matching pair of frames (same stance phase, pose and cloth nearest), so
  the loop plays without a seam; one-shot behaviours (jump, turn) run from rest to rest. Each recording is drawn in
  eight directions by turning the character on the spot before recording (the motion is the same; the view sector is
  the direction's), at the skin's own size and the page's camera.
- **Export.** A sprite sheet PNG (one row per animation and direction, frames in order, cells of one size with a
  shared anchor at the ground under the root) and a JSON file in the Aseprite JSON array format that engines and
  tools already read: frames with their rectangles and durations, `frameTags` naming each animation and direction,
  and the anchor as a slice pivot. Then `.aseprite` files (the documented binary format: one layer, tags per
  animation and direction), written without a dependency.
- **One command line.** `pinata` (a `bin` in package.json) with subcommands over what exists: `new` (a starter),
  `check` (the gates and hints), `skin` (preview and fit), `render` (stills and strips for looking) and `export`. Every
  subcommand prints what it wrote and exits non-zero on a failed gate whose fix is in the character's files, with the
  hint naming the file to fix; gates that measure the engine itself (feet held and facing in exports, which no
  character file can fix) are printed as engine notes and do not fail an author's command.
- **MCP server.** `pinata mcp` speaks the Model Context Protocol over stdio (JSON-RPC 2.0; the protocol is small, so
  no SDK dependency): one tool per subcommand, with the same arguments and the same results as the command line,
  plus the authoring guide as a resource. Claude Code and other clients use it directly.
- **Behaviours.** Walk, run, turn and jump exist. Phase 1 adds `idle` (a standing take with breathing and weight
  shifts, from CMU), `crouch` and one simple attack (CMU takes, the knight's with its sword held by the existing
  style), each a recorder script and a gate.
- **Authoring hints.** The P5 authors' notes go into the guide and the hints: decals for small features,
  stride-to-leg-length guidance, palette budgeting, radius against diameter, a reliable edit path for agents; and the
  skin artist's guide joins the authoring guide so one document covers a character end to end.

## Gates (fixed before implementation)

| Gate | Threshold | Notes |
|---|---|---|
| Existing outputs | byte-identical, except outputs named as meant to change | the page and its gates untouched |
| Same input, same export | exporting a character twice gives byte-identical files in Node | determinism per engine |
| Seamless loops | for every looping animation and direction, the pixels changed between the last frame and the first are at most the median changed between consecutive frames of that loop | |
| Feet held in exports | in every walk and run loop, a planted foot's sole pixel moves at most 1 px between frames of one stance | the page's standing rule, on exported frames |
| Every direction | each animation exported in eight directions; a blind panel of the eight idle frames per character names each direction (front, front-left, ...) correctly in at least 90% of answers | facing reads |
| Round trip | an independent reader in the tests rebuilds every exported frame from the sheet and the JSON, and from the `.aseprite` file, bit-exactly | |
| CLI and MCP agree | for every subcommand, the MCP tool with the same arguments writes byte-identical files and returns the same status | a scripted client in the tests |
| Behaviours read | for idle, crouch and the attack, a blind panel names the action from its side-view strip (from a list including distractors) in at least 2/3 of answers per behaviour | |
| Exit test | three prompts for characters with capes, each given to one fresh agent with only the authoring guide and the MCP server (no repository context): each reaches a skinned, exported character passing every gate within 10 `check` runs; three fresh judges match the exported idle sheets to the prompts, passing if each judge matches all three or at least 2 of 3 judges do | the roadmap's exit |

## Batches

- **A. Recorder and export:** recorded idle, walk, run, turn and jump in eight directions for the four humanoids; the
  sheet and JSON; the loop, feet, determinism, direction and round-trip gates (the `.aseprite` part of the round trip
  waits for C). Review.
- **B. One command line and the MCP server:** `pinata` with its subcommands; `pinata mcp`; the agreement gate; the
  guide as a resource; Claude Code configured with the server in the repository's own `.mcp.json`. Review.
- **C. Behaviours and Aseprite:** idle from capture, crouch, the attack; `.aseprite` export; the behaviours gate.
  Review.
- **D. Authoring and the exit test:** the hints and the guide; the exit test; release. Review.

## Results

### Batch A: recorder and export

Code: `src/export/` (`record.ts`, `loops.ts`, `gates.ts`, `report.ts`, `sheet.ts`), `src/page/sprite.ts` (the page's
drawing, shared), `src/judge/choice.ts` (labelled panels), `npm run export -- <character dir> <out dir>` and
`npm run direction-panel`. Choices are in [`design.md`](../design.md#export-srcexport). The four skinned humanoids are
recorded in idle, walk, run, turn and jump, each in eight directions (160 tracks, 1,248 to 1,600 frames per
character). Cells: knight 70x67, rogue 36x46, dwarf 56x44, wizard 50x76; sheets: knight 4060x3216, rogue 1620x1840,
dwarf 3248x1760, wizard 2500x3040 (none over 4096 px; long tracks wrap onto further rows).

The eight idle loops print `n/a`. Frames per track: idle 12; walk 50 (knight), 45 (rogue), 55 (dwarf), 30 (wizard); run
15, 30, 30, 17; turn 57, 41, 42, 47; jump 66, 43, 58, 50. Recording and drawing one character takes 2 to 6 s. No pixel
on a cell's border in any frame.

Direction panel (`npm run direction-panel`: 32 items, one scaled idle frame each, shuffled, in
`reports/export-panel/packet/`, the key outside it; the spec has `"kind": "choice"`, the judge tool's labelled
panels, tests in `test/judge.test.ts`). Three judges (opus, sonnet, haiku), each shown every character once in each
direction: correct in 44 of 96 answers, 46% against the gate's 90%, **missed**. By character: knight 17/24, rogue
12/24, dwarf 9/24, wizard 6/24; by judge 19/32, 13/32, 12/32. By direction (12 answers each): front 10, front-right 3
(named front 7 times), right 5, back-right 2, back 7 (named front 5 times), back-left 1, left 8, front-left 8. Every
character's eight idle frames were looked at and each is drawn in the right view; the misses are readability: the
wizard's back and back-three-quarter views show a white patch at the head that reads as a beard or face, so back
reads as front, and three-quarter views read as front or side. Each judge saw each character once per direction, so
elimination could only have inflated the score.

Seen on the sheets: walks and runs read as the page's characters, capes trail on runs and hang on walks, the turn
passes through the intermediate views, the jump crouches, rises and lands inside the cell. The dwarf's axe and cloak
make its cell wide (56 px against 44 high).

Open: the feet-held gate on drawn pixels and the direction panel (readability of the skins' views, the wizard's back
first); the rogue's boots below the ground line; the frame counts of walk (30 to 55) differ by character because a
cape or cloak has its own period, so a walk is two strides where the cloth needs it; `travel` is not part of
Aseprite's format.

### Batch B: one command line and the MCP server

Code: `src/tool/` (`commands.ts`, `check.ts`, `new.ts`, `skin.ts`, `render.ts`, `export.ts`, `io.ts`, `subject.ts`,
`mcp.ts`), `src/cli/pinata.ts` (the `bin`), `.mcp.json`, `test/pinata.test.ts`. The npm scripts `check`, `new`, `skin`
and `export` are entry points over the same functions. Choices are in
[`design.md`](../design.md#command-line-and-mcp-server-srctool-srcclipinatats); the guide
([`authoring.md`](../authoring.md)) covers `pinata` and the server.

| Gate | Result |
|---|---|
| Existing outputs | met, with the changes meant: `npm run rendering-panel` output is byte-identical except the six rogue strips (`rogue-{walk,turn,fall}-{strip,rotate}.png`), which changed because the rogue's `skin.json` changed (foot pivots; meant). The old `check` (dog), `new`, `skin guide` and `skin fit` print the same lines and write the same files (only timing figures differ); `skin preview` of the rogue differs only in the turntable flicker figure (10.37% to 9.87%) and its images, from the same skin change; `npm run export` writes the same `.png` and `.json` as `pinata export`. Changed on purpose in the old scripts: `export` prints the new report format and exits 0 when only engine gates miss, refuses extra arguments (exit 2) and exits 2 with a message for a character that cannot be recorded; `skin` exits 2 with a message when a file it reads is missing (it ended on an uncaught error); `check` prints a file error's message without a stack. `npm test` (737 tests), `npm run typecheck` and `npm run site && npm run test:browser` pass |
| CLI and MCP agree | met: a scripted client spawns `pinata mcp` and, for thirteen cases covering every subcommand (`new` into a new and into an occupied directory, `check` with `out`, without `out` (the report in the character's directory), on an invalid package and with `out` a file, `skin guide`, `preview` (default, `clean`, and a skin that does not fit: status 1), `fit` with `scale` and `pixelsPerMetre`, `render`, `export` of the rogue and of an unskinned character), runs the tool and the command with the same arguments into separate directories. The printed lines (paths and timings normalised), the files (`metrics.json` without its timing figures, `summary.txt` without its directory) and the statuses are equal, and `isError` is set for every non-zero status. Further tests: a result lists only what the command wrote and a refusal lists nothing, `check` removes only its own report files, unknown arguments and wrong types are errors naming the argument. The agreement test takes about 15 s |

Exit codes and engine notes: `export` reports `feet`, `facing`, `border` and `anchor` misses as `note` lines that do not
set exit 1; `ground` and `loop` fail with a hint naming the file. `ground` is measured in the side views only (idle
right and left; the reason is in the design notes), with a signed offset and its own hint for feet below and feet
floating, and fails when no sole pixel is visible. The left view is an engine note (`mirroredGround`): it draws each
foot's sprite on the other foot's bone, so an asymmetric rig puts a foot off the line that no skin can correct.
`idle-right` passes for all four (knight 1 px below, rogue 1 below, dwarf 1 below, wizard 1 above) with the rogue's foot
pivots raised; `idle-left` reads knight 2 px below, rogue 3 above, dwarf 1 below, wizard 2 above. `pinata export` exits
0 for all four (15 to 17 engine notes each, `feet` and `mirroredGround`). The idle loops stay `n/a` until batch C.
`pinata` with no arguments or `help` prints the usage and exits 0; an unknown command prints it and exits 2.

The server speaks `initialize` (versions 2025-06-18 and 2024-11-05 accepted, otherwise 2025-06-18; 2025-03-26 needs
batch arrays and is not accepted), notifications, `ping`, `tools/list`, `tools/call` (tools `new`, `check`, `skin`,
`render`, `export`), `resources/list` and `resources/read` (`pinata://docs/authoring`); malformed JSON, a message
that is not a JSON-RPC 2.0 object, unknown methods, tools and resources, and bad parameters are JSON-RPC errors
(-32700, -32600, -32601, -32602, -32002); every command failure, a failed gate and an invalid argument included, is
an `isError` tool result with the same status as the command line. A running command blocks the server (2 to 6 s for
`render` and `export`). While serving, every console method and `process.stdout.write` write to stderr.

Open: the left-view `ground` measurement (above); `pinata` runs from a checkout only, since Node does not strip
types under `node_modules` (a built JavaScript bin is a follow-up in the TODO); the server is checked by a scripted
client, not yet by Claude Code itself or other clients; the exit test (batch D) is the first real use by an agent.
